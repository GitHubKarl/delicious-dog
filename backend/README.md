# 美食转盘 · 后端（预留）

> **当前状态：空目录，未启动任何服务。**
> 首期小程序是纯离线版本，所有数据在客户端本地，后端完全不参与。这里的规划是给「在线版」留的口子，不是现在要写的代码。

## 为什么首期不做后端

| 维度 | 首期（离线） | 需要后端时 |
|---|---|---|
| 品类数据 | 本地 `uni storage` | 云端同步、多端一致 |
| 用户 | 无登录、无账号 | 需要跨设备 / 收藏 / 历史 |
| 合规 | 不采集任何用户数据，个人主体审核压力最小 | 一旦存用户数据，要隐私协议、数据安全、备案 |
| 成本 | 0 | 服务器 + 数据库 + 运维 |

结论：先上线验证「有人愿意用」，再决定要不要为同步能力付这些成本。

## 技术选型（已定，未落地）

Spring Cloud Alibaba 体系，和本机已有的环境对齐：

| 层 | 选型 | 说明 |
|---|---|---|
| 运行时 | JDK 21（`D:\develop\java21`） | 本机已装 |
| 构建 | Maven 3.9.16（`D:\develop\maven`） | 本机已装，本地仓库在 `maven/mvn_repository` |
| 框架 | Spring Boot 3.x + Spring Cloud Alibaba | 版本对齐 Boot 3 的 SCA 版本线 |
| 注册/配置 | Nacos | 首期单机版可先不启，用 `spring.cloud.nacos.discovery.enabled=false` 关掉 |
| 网关 | Spring Cloud Gateway | 单机版可省，多服务时再加 |
| 限流熔断 | Sentinel | 上量后再接 |
| ORM | MyBatis-Plus | |
| 数据库 | MySQL 8 | 品类模板、用户自选品类 |
| 缓存 | Redis | 首个版本可不接 |

**单机版优先**：先用一个可独立启动的 Spring Boot 模块跑通，别一上来就拆微服务。Nacos / Gateway / Sentinel 都是「有第二个服务」或「有流量压力」时才需要。

## 预期服务划分（等真的要做时再定）

首期若只是云同步品类，一个模块足够：

```
backend/
└─ wheel-service/            Spring Boot 单体，端口 8080
   ├─ controller/            对外 REST
   ├─ service/
   ├─ mapper/                MyBatis-Plus
   └─ entity/
```

拆微服务的前提是出现第二个业务域（例如「附近餐厅推荐」），现在还看不到。

## 预留接口草案（未实现）

只列形状，路径和字段都还会变：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/categories/default` | 拉取官方推荐的品类模板 |
| GET | `/api/v1/categories/mine` | 拉取当前用户自选品类（需登录态） |
| PUT | `/api/v1/categories/mine` | 覆盖式保存用户品类（≤12 个） |
| GET | `/api/v1/health` | 健康检查 |

设计约束：

- 品类数量上限（3~12）在前后端都要校验，前端是体验，后端是真相
- 一切写接口都要登录态；没有登录的接口只读
- 首期前端没有 token 概念，接入时需要先在 `frontend` 加登录流程（微信静默登录 + 自建会话）

## 真要启动时，需要先准备

1. MySQL 8 实例（本地或云），建库 `delicious_dog`
2. 确认 JDK / Maven 环境变量生效（`java -version`、`mvn -v`）
3. 决定是否接 Nacos：单机版直接关掉，别为了「架构完整」先起中间件
4. 小程序侧要开通微信登录能力（个人主体可用，但需要用户授权拿 openid）

## 明确不做的事（避免过度设计）

- 不做用户画像 / 埋点采集：和首期「不采集数据」的定位冲突，且个人主体审核风险大
- 不做推荐算法：品类只有 12 个，随机就是最好的策略
- 不做管理后台：品类模板改一次代码就能发版
